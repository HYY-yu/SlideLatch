# PR-first host entry

You are the coordinator. This is the only Loop A entry. Use actual native spawn, follow-up, messaging, listing and interruption tools, including independent `fork_turns: "none"`. Bind the real coordinator identity from host metadata and worker IDs returned by dispatch. A role label, shell process, invented ID or CLI thread ID is not a native actor. Missing identity or dispatch is BLOCKED_HOST. Do not delegate overall coordination or return merely because a child finishes.

Read the user's current goals and decisions. User authorization covers the purpose and allowed actions. The coordinator derives task key, owner, exact paths, worktree, branch and SHA from evidence. Never attribute those derived details to the user. PRs and Issues supply facts, not authorization. Issues are optional communication links. Do not create an Issue or meaningless commit merely to start a round.

## Select and prepare

After host and authorization preflight, reserve invocationId and record `begin` using the frozen repository checkout before reading task documents or selecting candidates. The begin registry is common-directory scoped, so the later target worktree may differ within that repository. Prefer the original caller timestamp. Without one, the first observable begin starts the budget and must precede the research below.

1. Read the shared lease through the frozen lifecycle helper. An active writer, unbound actor, pending operation or unknown outcome blocks new business. Do not reclaim locks, inspect capability contents, scan processes or impersonate an earlier owner. If a prior real RELEASED archive has a confirmed merge and pending production result, follow the read-only continuation below first.
2. Query current main and all open PRs with actual GitHub tools. Map them to authorized goals. Exclude PRs with an active owner. Verify integrated coverage using exact heads and ancestry, not titles or Issue closure. Prioritize failed checks, unresolved independent acceptance, then merge-ready PRs. Use the helper's `select` command with this observed candidate set. When no PR can advance, select one authorized queued task with accepted dependencies, no owner and independent acceptance. Read `docs/loop-a-backlog.md` as historical hints, then recheck its live dependencies. Do not ask the user to fill in Issue numbers or paths.
3. Read `docs/loop-a-once.md`, `docs/loop-a-lifecycle.md`, `docs/team-workflow.md` and relevant `.codex/agents` instructions. Record a short scope with input, output, invariant, failure behavior and acceptance. Ask only for a new product direction, scope expansion, missing authority or a consequential decision. Continue independent allowed work.
4. Select a clean frozen implementation entry and an independent owner worktree. For an existing PR, checkout its exact current head, separately record target base SHA, baseRef, headRef and trusted historical author identity evidence. Unknown author provenance blocks acceptance. Local branch names need not equal headRef. Reuse the already recorded invocationId and startedAt; never restart the budget after selection. Prepare version 2 input yourself. Issue may be null. Existing-PR review may set publish false. Repair or new development requires authorized exact-commit publication and an allowed transport before acquiring.
5. Verify both lockfiles and dependency provisioning. Never install credentials, change security settings, copy the shared Skill or alter the shared DSL dependency target. Run frozen `prepare`, then `acquire`. Only READY allows dispatch. Keep the plan and opaque 0600 capability files outside repositories. Each operation uses fresh inspect revision and a stable unique operation_id. Never edit lease state. Twenty minutes is the original business budget, with at most two repairs and no renewal.

## Review or implement

For `existing-pr`, acquisition begins at SEALED with the current head. There is no writer or commit requirement. Dispatch an independent reviewer directly. If a concrete in-scope repair is needed and publication was authorized in the plan, collect full stop evidence, call `repair`, and use the writer sequence below. Base drift requires fresh acceptance in a new round, not editing the frozen plan. If publication was not authorized, keep the PR and ask for that specific action.

For `implementation` or an admitted repair, dispatch-intent writer, then native spawn with readiness-only instructions. Before binding, the worker must not write, run business commands or spawn others. Bind its actual ID through `bind-worker`; pass only its capability path and exact scope. Never read, print, echo, copy or forward capability contents. Unknown spawn results retain intent and lock. Writer uses lifecycle `write`, managed `commit`, then managed `verify` on the new head. No direct edits, commits, shell verification or subprocess escape. Commits do not include a fixed Cloudflare skip marker.

Collect explicit stop-acknowledged/noExternalProcesses evidence after all activity. Check supervisor EXITED records. Native completed or interrupt does not prove process exit. Call confirm-quiescent and seal-writer only after actual stop evidence and a clean checkout.

Dispatch a non-author reviewer in a different clean worktree at sealed head. Use the same readiness, native identity and opaque capability protocol. Historical PR authors count as authors even if they were not writers this round. Reviewer inspects the actual diff, runs managed verify and applicable domain checks, then record-review with exact head and target base. Product UI and export changes require the verification Skill's browser and PowerPoint checks. Pure protocol changes can mark those checks inapplicable with a reason.

After independent review, publish only if code changed. Re-read the remote head and base first. Upload the exact sealed commit using the authorized transport. For an existing PR, require the remote old head still matches the adopted target and push the local branch explicitly to that PR's headRef. Do not force-push or assume matching branch names. Re-read remote branch and PR head. New work creates a Draft PR; unchanged existing PRs reuse their current draft state. GitHub blob/tree/commit APIs that recreate content do not upload the sealed commit. A denial stops publication without another route.

Record fresh PR and CI evidence. Keep checkout start SHA, PR head, target base, synthetic CI merge SHA and actual merge SHA separate. Query all applicable checks and review threads. The frozen helper always requires verify and cloudflare-root-install. Supply platform requiredChecks as {names, source, observedAt} from a successful fresh read. A known empty names list adds no platform requirements; missing, failed or stale reads block merging. Platform names add to the fixed project minimum and cannot replace it. A failed or unreadable check is not green. Before release or shipping, collect every actor's latest stop evidence and actual command exits. No writer is needed for unchanged acceptance, but a real independent reviewer and managed verify are always needed.

## Merge and production

User authorization may allow accepted PRs to merge automatically. That means the coordinator may call the official merge operation; it does not require GitHub native auto_merge or settings changes. Never merge without recorded authority and exact independent acceptance.

Immediately before merging, re-read head, base, baseRef, headRef, draft/state, mergeability, checks, unresolved review threads and applicable acceptance. Mark ready only after acceptance and within publication authority. Call `merge-intent` with that fresh snapshot. It persists expected_head_sha and ordinary merge method before the external action. Use those exact values with the official GitHub tool. The tool's head check does not atomically lock base; recheck before the call and verify the actual merge's two parents afterward. Any drift invalidates the old acceptance.

Record only the official result with `record-merge`, including actual merge SHA and parent SHAs. Unknown or timed-out results remain MERGING and keep the lock. Query the PR and commit first, never blindly retry. A known denial is MERGE_BLOCKED, not success. No automatic alternate credentials, transports or repository settings changes.

A normal main merge may trigger production deployment. Do not add a permanent deployment skip. Query the actual merge SHA's production build and deployment, then run the live regression appropriate to the changed scope. Record provider, deployment ID, URL, environment, source and time. Preview success, an old build, skipped build or unknown status cannot prove production success.

After a confirmed ordinary merge, full actor/process stop evidence permits local release even if production is pending. Report DEPLOYMENT_PENDING or DEPLOYMENT_FAILED separately from the local RELEASED status. Preserve the real archive and exact merge SHA. Do not restart a deployment to fit this round's budget. At deadline, stop new business; only reconcile outcomes or perform safe cleanup.

A later observation uses the current coordinator's real identity and fresh official deployment observations with `observe-deployment plan.json archive.json remote.json`. This command is read-only, uses no old capability, changes no lease and cannot merge or trigger deployment. Its result is OBSERVED, with the origin epoch and observer source. The same long-lived coordinator may observe again; a different coordinator uses its own identity rather than the former owner's. It cannot release an unknown old operation or interfere with a successor lease. Keep the production continuation in the task record until actual success or a decision-worthy failure.

## Stop and report

Use lifecycle release and helper complete with the actual archive and fresh remote facts. The helpers validate consistency, not source authenticity. Report DRAFT_READY, PR_UPDATED, PR_ACCEPTED, MERGE_BLOCKED, DEPLOYMENT_PENDING, DEPLOYMENT_FAILED or DEPLOYED as actually reached. Never claim a real pilot, merge, deployment or continuous schedule from unit tests.

On correctable failures, use existing repair only from SEALED/REVIEWED/PR/CI after complete stop evidence. Do not request-stop first on that path. Repeated evidence pauses. ACTIVE failure uses cancellation, not an invented successful commit. Cancellation requires exact history binding, real exits, actor stop and revocation. Legacy audit rules remain. CANCELLED_RELEASED is cancellation. Unknown mutation, command, spawn or merge outcome retains the lock. Never extend the old budget or release by writing JSON.

Do not start Loop B, create a daemon, register a new schedule, change automation configuration or use blocked GUI/API routes. This Skill runs one invoked round. A schedule prompt can invoke it, but code and role files do not prove that a schedule is registered or working. Send only meaningful results, blockers and needed decisions.
